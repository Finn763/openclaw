Closes #128826

## What Problem This Solves

Fixes an issue where users with the externalised Codex plugin installed (the default layout for published OpenClaw installs) would see `openclaw doctor --lint` and `openclaw doctor --json` abort before running any check:

```
MissingPublicSurfaceError: Unable to resolve bundled plugin public surface codex/api.js
```

The published core package deliberately excludes `dist/extensions/codex/**` (`package.json` "files"), so the bundled-only loader in `registerBundledHealthChecks` can never resolve the Codex health surface. Because registration runs before any check selection, no flag (`--only`, `--severity-min`, `--skip`) can avoid the abort. This kills CI preflight, review gates, and scheduled health checks for anyone using Codex.

## Why This Change Was Made

Codex doctor checks now resolve through a registry-aware path that mirrors the existing trusted external-plugin surface resolution used for provider policy artifacts (`resolveTrustedExternalProviderPolicySurface`): the bundled surface is tried first (unchanged for dev/source checkouts), and when it is absent the manifest-selected, `trustedOfficialInstall`-verified Codex install root is loaded via `loadPluginPublicArtifactModuleSync`.

The fallback trigger is intentionally narrow: it fires only when the bundled `codex/api.js` surface is directly absent (bundled candidate resolution returns `null`). A `MissingPublicSurfaceError` raised while loading an already-resolved bundled artifact propagates unchanged and never falls back to the external install, so a real bundled-surface failure cannot be masked as a missing bundle.

The fix deliberately does not turn the missing bundled artifact into a silent no-op: if neither the bundled surface nor a trusted official Codex install can be resolved for a configured Codex runtime, registration fails loudly with a `MissingPublicSurfaceError` that names both attempted locations, so Codex diagnostics are never dropped silently.

## User Impact

- `openclaw doctor --lint` / `--json` complete normally on published installs with the externalised Codex plugin and now register the real `codex/managed-app-server` check from the installed plugin.
- Dev/source checkouts that still ship the bundled Codex extension behave exactly as before.
- A genuinely broken setup (Codex configured, but no bundled surface and no trusted official install) still fails loudly with an actionable message instead of silently skipping Codex checks.

The broad `catch (error instanceof MissingPublicSurfaceError)` in `loadCodexManagedHealthApi` also swallowed nested missing-surface errors raised while loading a *resolved* bundled artifact, misdiagnosing a real bundled failure as "bundled absent" and silently loading the external API. Fixed:

### Packaged-install simulation (live CLI)

Ran the real CLI against a scratch directory that replicates the published install layout instead of the dev checkout (in a dev checkout the bundled Codex surface always resolves from `extensions/codex/`, which is why this bug only exists for published installs):

- **Package root**: repo `package.json` + `openclaw.mjs` + `node-version.mjs` + a copy of `dist/` with `dist/extensions/codex/**` removed — mirroring the published package's `"files"` exclusions (`!dist/extensions/codex/**`). No `extensions/` source tree, so the bundled codex surface cannot resolve.
- **External plugin**: the real published npm package `@openclaw/codex` (tarball `2026.8.1-beta.3`; the stable `2026.8.1` is not on the registry yet) extracted to a directory outside the package root. The published `2026.7.1-1` layout has no `dist/api.js` at all — that is exactly the pre-fix published shape that triggers this bug; the beta ships the doctor surface.
- **Install record**: seeded into a scratch `OPENCLAW_STATE_DIR` via the project's own `writePersistedInstalledPluginIndexInstallRecordsSync` with the shape `openclaw plugin install @openclaw/codex` persists for a registry install (`source: "npm"`, `spec/resolvedName: "@openclaw/codex"`, no `artifactKind`/`sourcePath`), which is what `isTrustedOfficialPluginInstall` requires.
- **Config**: `agents.defaults.models["openai/gpt-5.6-sol"].agentRuntime.id = "codex"`, so a Codex harness runtime is configured.

### Boundaries (what this simulation does not cover)

- The core package was not literally `npm pack`ed and installed globally. The scratch layout replicates the published `"files"` whitelist (minus `dist/extensions/codex`) and shares dependency resolution with the dev checkout via a `node_modules` junction. The doctor registration path under test — bundled-surface absence + trusted external install — is identical to the packaged layout; packaging itself is not what this PR changes.
- The external plugin is the real published npm package, but from a `2026.8.1-beta.3` tarball because the stable `2026.8.1` is not yet on the registry. Its manifest (`id: "codex"`, `dist/api.js` exporting `registerCodexManagedAppServerDoctorChecks`) is what the released stable package will ship.
- The install record is seeded through the project's own persistence helper rather than a live `openclaw plugin install` network run (kept offline/deterministic); the record shape matches the installer's persisted output, and the trust check paths are exercised for real (npm-trusted passes; path-source fails).
